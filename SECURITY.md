# Security Policy

## Supported Versions

Only the current development tip (`main` and active release branches) is supported with security updates.

## Reporting a Vulnerability

Please **do not** open public GitHub issues for suspected security vulnerabilities, driver-crash exploits, unsafe FFI memory corruption bugs, or credential exposure.

Report vulnerabilities privately through GitHub Security Advisories for this repository, including:

1. Affected crate, CLI subcommand, or runtime integration (`forge-device`, `forge-runtime`, etc.).
2. Windows build, AMD Adrenalin driver version, and GPU `gfx` target.
3. Minimal reproduction steps or proof-of-concept input.
4. Observed impact (process crash, out-of-bounds memory access, DLL hijacking, or GPU reset/TDR).

## Security Design Expectations

- **DLL Loading** (`forge_core::loader`): no native library is loaded by bare name, so the Windows default search order (application directory, current directory, `PATH`) is never used.
  - *System and AMD-driver libraries* (`ntdll.dll`, `pdh.dll`, `vulkan-1.dll`, `amdadlx64.dll`, `amfrt64.dll`) are resolved only inside the directory returned by `GetSystemDirectoryW` and loaded by absolute path with `LOAD_LIBRARY_SEARCH_SYSTEM32`.
  - *Vendor SDK libraries* (the HIP runtime, `amdhip64_*.dll`) are accepted only if their canonical path (symlinks, junctions and `..` resolved) lies under System32, `%ProgramFiles%` or `%ProgramFiles(x86)%`, obtained from `SHGetKnownFolderPath` rather than environment variables. `HIP_PATH` / `ROCM_PATH` only add candidates; a candidate outside those roots is rejected and reported, never silently replaced by a bare-name search. A HIP SDK installed elsewhere (for example `D:\ROCm`) is therefore not detected; the driver's System32 copy is still used.
  - Dependencies of vendor libraries resolve from their own directory and System32 only. After loading, the module's real path is read back and compared with the validated path.
  - Failures are typed: not installed, refused (untrusted location), or rejected by the OS loader. The loaded path is reported by `forge doctor --json` for ADLX, HIP and Vulkan.
  - `llama-bench` and Python are *executed*, not loaded. `llama-bench` paths must resolve to an existing `llama-bench*.exe`. The Python interpreter is a user choice and is not restricted to an install location, but an explicit `--python` must be an existing regular file, a bare `python` is resolved from `PATH` only (never the application directory or current directory), and `.bat`/`.cmd` files are refused on Windows. Both are launched with structured arguments, never through a shell. `reg.exe` is launched from System32 by absolute path. Note: `forge bench triton` runs a script found relative to the current directory by default (`modules/ai/triton/bench_suite.py`); run it from a repository checkout you trust or pass `--script`.
- **GPU Tuning Safety** (`forge tune`): read-only by default. `power-limit` and `reset` mutate only with `--apply`; requested values are validated against the hardware range and step reported by ADLX. A power-limit change runs a fixed sequence: read the original value, validate, write, read back, compare, and if the read-back contradicts the request (or a rejected write left the value changed or unknown) write the original value back and read that back too. Results report the operation (`NOT APPLIED`, `CONFIRMED`, `NOT CONFIRMED`) and the rollback (`NOT NEEDED`, `ROLLBACK ATTEMPTED`, `ROLLBACK CONFIRMED`, `ROLLBACK FAILED`) separately, and the CLI exits non-zero unless a change is `CONFIRMED`. An accepted write whose read-back is unavailable is `NOT CONFIRMED` (there is no "applied but unverified" status that could be read as success): the original value is written back and the rollback is reported as `ROLLBACK ATTEMPTED` if that restore cannot be read back either, or `ROLLBACK CONFIRMED` if it can. A factory reset discards the previous tuning profile, which is not captured, so it is reported as `ROLLBACK UNSUPPORTED`. For a factory reset the API result and the GPU state are reported separately: the API is `ACCEPTED` (ADLX_SUCCEEDED) or `REJECTED`, with the raw `ADLX_RESULT` kept, and the state is `CONFIRMED` only when the read-back shows factory settings. The state is read back after every call, because an error does not prove nothing changed and a success does not prove the GPU reached factory state. Only a factory read-back is `CONFIRMED` (even after an error, with the error text kept); a non-factory or unreadable read-back is `NOT CONFIRMED`, whether the call was accepted or rejected. `NOT APPLIED` appears only for a dry run or a GPU that was already at factory settings. The CLI exits non-zero and the desktop shows an error unless the state is `CONFIRMED`. There is no automatic overclocking, no voltage or fan changes, and nothing is tuned at startup. **The state machine is verified against a scripted fake backend. On real hardware (RX 6900 XT, `gfx1030`, Adrenalin 26.11.2) only the power-limit write path has been exercised, once: `0%` -> `-1%` -> `0%`, each step `CONFIRMED` by an ADLX read-back (rollback `NOT NEEDED`). The rollback path (a contradicting read-back or a rejected write) and `ResetToFactory` have not been run on real hardware.**
- **Configuration Patching** (`forge llm apply-lmstudio`, `apply-env`): dry-run by default and prints the exact files and `HKCU\Environment` keys it would change. An existing LM Studio config that is not a valid JSON object is refused rather than replaced. Backups (`.json.bak`) are never overwritten, so repeated applies keep the original; writes use a temp file and rename, and the result is re-read and verified. Unrelated user fields are preserved. Model paths containing `..` cannot move the written file outside the LM Studio config directory. Nothing is sent over the network.
- **Desktop trust boundary**: the Tauri window loads only bundled assets under a strict CSP (`default-src 'self'`) and has only the `core:default` capability (no filesystem or shell plugins). The backend does not trust the frontend's `dry_run` flag: every mutating command (power limit, factory reset, LM Studio patch, env/Ollama patch and both rollbacks) validates its inputs first (power limit within +/-100%, 16-bit PCI id, bounded device index, plain profile id, existing `.gguf` model path, strict `kv_quant`) and an apply is authorized only by a successful dry-run preview with identical parameters in the same process, valid for 15 minutes and usable once, **and made for the same physical GPU**: the backend resolves the target GPU itself (vendor id, device id, PCI bus id and name; the enumeration index only as a labelled fallback when no bus id is reported) at preview time and again at apply time, and refuses the apply if it changed. Targets that cannot be told apart (two identical cards sharing a device id, or several discrete cards with no PCI id given) are refused instead of guessed. Power limit, factory reset, the LM Studio patch and the env/Ollama patch are GPU-bound; both rollbacks restore files or registry values independent of any GPU and carry no device identity. A missing `dry_run` field defaults to a dry run. The app is still local software that can change your configuration when you press Apply; it is not a sandbox against a compromised webview that can also request the preview.
- **Supply chain**: CI uses actions pinned to commit SHAs, read-only `GITHUB_TOKEN` permissions by default (write access only in the release publish job), `--locked` builds against the committed `Cargo.lock`, and `cargo-deny` (RustSec advisories, a license allow-list, crates.io-only sources; see `deny.toml`).
- **Bounds & Allocation Checks**: GPU compute wrappers validate non-zero dimensions, checked arithmetic, `maxBufferSize`, and VRAM capacity before allocating or dispatching device buffers.
- **Secrets & Privacy**: Diagnostic reports (`forge doctor --json`) inspect local hardware and Python paths; review output before posting publicly if directory paths contain local usernames.
